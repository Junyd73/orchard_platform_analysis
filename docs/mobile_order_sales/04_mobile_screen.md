## 0. UX (DEC-021)

- 같은 정보 **두 번 입력하지 않음** (생산수량 → 판매 재입력 금지, A안)
- 배정·출고는 **선택 경로** — 미배정을 오류/경고로 강조하지 않음
- 날짜·채번 자동 · 필드 최소화 · Batch 번호 사용자 입력 금지
- **여러 상품 일괄선택** (재고·경매 · HARVEST 복수)
- **내부키 비노출:** `work_id` · `stock_seq` · 출하 내부번호 · 생산확정키
- 경매 출하도 **최소입력** — 시스템이 아는 규격·가용·최근 시장/법인 자동
- **시장/법인**은 최근 **유효 조합** 우선 (규칙 §5B.1)
- **내부 상태코드**와 **사용자 라벨** 분리 (OPEN-SHIP-STATE ≠ 화면 문구)
- 개발용어 STOCK / DIRECT / DRAFT / TRANSIT 등을 **사용자에게 직접 노출하지 않음**
- **새 최상위 탭 추가 금지** — 기존 4탭 유지
- 기존 **주문·직접판매** UX는 경매 개정으로 **훼손하지 않음**
- **경매 출하 ≠ 판매** ([DEC-036](./07_decisions.md))

## 4. 주문 등록/수정

- 고객 (이름·연락처 필수)
- 주문일 기본 `today_ops` → 저장 `YYYY-MM-DD`
- 출고예정일 (`planned_dt`)
- 시즌 `SS01`
- 상품 N행: 품종 · 중량 · 등급 · 크기/과수 · 수량 · 단가 · 금액
- 배송: 방문 / 택배 / (필요 시 화물)
- 방문수령 시 주소 비필수
- 선입금 · 메모

**검증:** 고객, 상세 ≥1, 행 수량 = 배송계획 합.  
**재고 0이어도 저장.** 가용 부족은 경고만.  
저장 시 판매 행 없음, `allocated_qty=0`.

수정: `stock_status='Y'` 이면 거부.

### 4.1 선입금 입력 (DEC-028 APPROVED · 설계)

```
선입금        [        0 ]원
              ↑ 0이면 아래 줄을 렌더링하지 않음

선입금        [  150,000 ]원
결제수단      [ 현금성 계정 ▾ ]   ← 금액 > 0 일 때만 표시. 필수
                                                (운영 코드 범위는 2단계 전 확정)
```

| 규칙 | 내용 |
|------|------|
| 표시 조건 | `pre_pay_amt > 0` 일 때만 **결제수단** 필드를 노출 |
| 필수 | 노출되면 필수. 미선택 저장 거부 |
| 0으로 되돌림 | 금액을 0으로 바꾸면 결제수단 값을 비우고 필드를 숨김 |
| 코드값 | 서버가 내려주는 **현금성 자산 계정** 목록만 사용(실제 운영 코드 재확인 후 범위 확정). 채권(외상·미수) 제외. **화면에 결제수단 코드 하드코딩 금지**. `get_account_codes('AS', …)` 전체 노출을 SSOT로 두지 않음 |
| 회계 | 주문 저장은 전표를 만들지 않는다 (DEC-009). 화면에 전표·수금 문구를 쓰지 않는다 |

**UI 용어 표준:** **결제수단** · **수금액** · **미수금** · **수금상태**.  
「수금방법」은 쓰지 않는다.

## 5. 주문 상세

헤더: 번호 · 고객 · **주문상태** · **재고상태(이행)** · 시즌 · 금액 · 선입금

규격별 줄 예:

```
주문 100    배정 30    미배정 70    출고 0
```

내부 계약: 「배정」= `allocated_qty`(누적). 「출고」= `shipped_qty`. 사용자에게 누적이라는 말을 쓰지 않음.  
미배정은 오류가 아니다. 안내: 「저장재고 출고 시 재고를 배정합니다.」 (DEC-020). 「미배정 → 반드시 처리」로 표시하지 않음.

배송 목록.

입금 영역 표시 (DEC-019 · DEC-028 · DEC-029):

| 표시 | 내용 |
|------|------|
| 선입금 | `pre_pay_amt` |
| 결제수단 | `pre_pay_method_cd` 명칭. 선입금 0이면 표시하지 않음 |
| 선입금 잔액 | `pre_pay_amt − CONFIRMED 판매에 적용된 선입금 합` (계산값) |
| 판매별 수금 | 연결된 판매 각각의 수금액·미수금 (판매 목록/상세에서) |

**주문완료 ≠ 수금완료.** 주문이 `ST010400` + `stock_status='Y'`(주문완료)여도 판매별 미수가 남을 수 있다. 두 개념을 한 배지로 합치지 않는다 (DEC-029).

출고 CTA: 배정잔량 있으면 기본 「배정재고 사용」(STOCK), 없으면 「일반재고에서 출고」(DIRECT). 개발 용어 STOCK/DIRECT를 화면에 쓰지 않음. 상세는 [§9](#9-stage-6-판매출고-화면-시나리오).

액션: 배정 · 배정해제(`release <= 배정-출고`) · 출고확정 · 취소(출고 전만)

부분출고 후 판매 탭에 판매가 여러 장 보인다 (DEC-017: 출고 1회 = 판매 1건). 연결 조회는 `t_sales_master.order_no`. 주문상세 잔여 표시 SSOT는 confirm 응답 `remaining_order[]`.

주문상태와 재고상태를 한 배지로 합치지 않음. ODS `OdsCard` 메타 두 줄 또는 칩 두 개.

| 규칙 | 내용 |
|------|------|

| 명칭 | 「판매예정」등 **판매 전용 문구를 경매와 공용하지 않음** → **「선택 n품목」** 등 중립 |
| 직접 판매 | **기존 기능 유지** (미리보기→판매/OUT) |
| 경매 넘기기 | **별도 CTA** — 판매 아님 · OUT 아님 |

**사용자 입력:** 각 상품 출하수량(담기 수량 기본, 가용 이하) · 시장/법인(최초 또는 변경 시).
**자동:** 출하일=오늘 · 최근 유효 시장/법인([§5B.1](#5b1-시장법인-자동선택-규칙-target)) · 품종/등급/중량/사이즈 · 가용.
**숨김:** `stock_seq` · 저장일 · 내부 출하키.

### 5B.1 시장·법인 자동선택 규칙 (TARGET)

1. 최근 사용한 **유효한 시장+법인 조합**이 있으면 **자동선택**
2. 사용자가 **시장** 변경
3. 기존 법인이 **새 시장에 유효한지** 재검증
4. 유효하지 않으면 법인 선택값 **초기화**
5. 최근값 없거나 최초면 **사용자 선택**

잘못된 최근 법인이 **다른 시장에 자동으로 붙는 UX 금지**. 물리 API·코드는 본 문서에서 **확정하지 않음**.

### 5B.2 경매 넘기기 확인 UX (TARGET)

- **`/orders/ship` (`ShipConfirmView`) 재사용 금지** — 의미(판매+OUT)와 충돌
- **바텀시트 / 짧은 확인 UI** 우선 (풀페이지 신규 최소화)

표시: 출하일 · 시장 · 법인 · 선택 품목 수 · 상품별 가용/출하수량 · 총 출하수량.
CTA: **`경매 넘기기`**
안내: 「아직 **판매확정이 아님** · 출하한 수량은 **판매 가능 재고에서 제외**」
내부어 DRAFT/TRANSIT **노출 금지**.

실제 컴포넌트·API 파일명은 **OPEN** (UI 단위 ODS/스텝퍼/시트만 재사용 가능).

|------|------|

| 확정 판매 | CONFIRMED |
| 소매 | `order_no` 있음 |
| 수출/도매 | 주문 없음 · source ORDER |
| **경매출하** | 출하 묶음 목록([§6.3](#63-경매출하-구역-target--dec-036)) |

카드(판매): 판매번호 · 일자 · 고객/법인 · 금액 · 미수 · 판매상태/수금상태 **분리 배지**.
상세: 규격 · 배송 · 수금(CONFIRMED만) · 판매초안이면 확정 CTA(기존 경로).

직접 판매: 고객 · 규격 · 수량 · 단가 · 배송 · 출고 포함 (기존).

한 주문에서 부분출고가 여러 번이면 판매 탭에 **판매 N건**이 같은 `order_no`로 나타난다. `t_order_master.sales_no`로 목록을 만들지 않는다.

### 6.1 판매 목록 필드 (후속 · 설계)

Stage 5 판매목록에서 추가로 보여줄 필드.

| 표시 | 소스 |
|------|------|
| 판매번호 / 판매일 | `sales_no` · `sales_dt` |
| 고객 | `custm_nm` |
| 판매금액 | `tot_sales_amt` |
| **수금액** | `tot_paid_amt` |
| **미수금** | `tot_unpaid_amt` |
| **수금상태** | 계산 배지 — 미수 / 부분수금 / 수금완료 |
| 주문 연결 | `order_no` 있으면 표시 |

**판매상태 배지와 수금상태 배지를 하나로 합치지 않는다** (DEC-029).

| 배지 | 값 |
|------|----|
| 판매상태 | 판매초안 / **판매확정**(CONFIRMED) — 화면에 DRAFT 영문 최소화 |
| 수금상태 | 미수 / 부분수금 / 수금완료 |

필터에 「판매완료」로 수금 여부를 섞지 않는다.

### 6.2 판매 상세 + 수금등록 (후속 · 설계)

```
판매 20260821-01        [판매확정] [부분수금]
────────────────────────────────
판매금액   300,000
수금액     150,000     ← 선입금 적용분 포함
미수금     150,000
────────────────────────────────
수금 내역
  2026-08-21  선입금 적용  150,000  현금/예금
────────────────────────────────
              [ + 수금등록 ]
```

수금등록 시트:

| 필드 | 규칙 |
|------|------|
| 수금액 | 필수. `> 0`. **미수금 이하**. 초과 입력 시 저장 불가 |
| 결제수단 | 필수. **현금성 자산 계정**(실제 운영 코드 재확인 후 범위 확정). 채권(외상·미수) 제외. 하드코딩 금지 |

| 조건 | 화면 |
|------|------|
| `CONFIRMED` + 미수금 > 0 | 수금등록 CTA 활성 |
| `CONFIRMED` + 미수금 = 0 | 수금등록 숨김/비활성, 「수금완료」 표시 |
| 판매초안(DRAFT) | 수금등록 **노출하지 않음**. 먼저 판매확정 (DEC-029) |

성공 후 판매 상세를 **서버에서 재조회**한다. 수금액·미수금을 클라이언트에서 재계산하지 않는다.

**UI 용어:** 결제수단 · 수금액 · 미수금 · 수금상태. 「수금방법」 금지.

## 9. Stage 6 판매/출고 화면 시나리오 (주문 · DIRECT)

**구현 (1차):** 화면 `ShipConfirmView` · 경로 `/orders/ship` · `POST /farms/{farm_cd}/shipments/confirm`. Vue **착수 완료**.
**API:** `POST /api/v1/farms/{farm_cd}/shipments/confirm` 만. FIFO·allocation·reserved는 Core.

### 9.0 경매와의 경계 (필수)

| | ShipConfirmView (본 절) | 경매 넘기기 (TARGET §5B) |
|--|-------------------------|---------------------------|
| 의미 | **판매 + OUT** | **판매 아님 · OUT 아님** |
| 화면 | `/orders/ship` | **별도** 시트/컴포넌트 (파일명 OPEN) |
| 재사용 | — | ODS · 스텝퍼 · 바텀시트 · 토스트 **만** |

경매 출하 의미를 ShipConfirm **동일 화면/API에 억지로 합치지 않음**.

### 9.1 한 화면, 세 진입 (주문/DIRECT)

```
생산 직후 ─┐
주문 상세 ─┼→ 판매/출고 화면 → confirm API
재고 화면 ─┘   (직접 판매 CTA)
```

판매 화면을 진입점마다 나누지 않는다. 차이는 **prefill** 뿐. (**경매 넘기기는 이 도식에 넣지 않음.**)

화면에 보일 것: 고객 · 품목(규격) · 수량 · 단가 · 주문 연결 여부 · 출고방식(농부 문구).
숨길 것: `stock_seq`, FIFO 분할, allocation consume, reserved.

확정 성공 후 잔여 **화면 SSOT** = `remaining_order[]` (줄 단위).
`remaining_order_qty`는 합 요약만. 완료 여부는 `order_status` (`ST010300`/`ST010400`). 무주문이면 둘 다 비움.

### 9.2 정책 4항

| # | 정책 | 내용 |
|---|------|------|
| 1 | 생산 직후 바로 판매 | 기본 **DIRECT**. 생산 IN 완료 후 prefill. **무주문 강제 아님**(설계). **1차:** 대형 주문검색 UI 없음 → 생산 진입은 무주문 DIRECT |
| 2 | 주문에서 출고 | 배정잔량 있으면 기본 「배정재고 사용」= STOCK. 없으면 「일반재고에서 출고」= DIRECT. 사용자가 변경 가능. 화면 라벨에 STOCK/DIRECT 금지 |
| 3 | 재고 탭 → **직접 판매** | 선택 n건 · 규격 prefill. `stock_seq` 강제 금지. Core FIFO. TARGET: 하단 **[직접 판매]** ([§5B](#5b-재고-선택--직접판매--경매-넘기기-dec-036--target)) |
| 4 | 주문 일괄/부분 출고 | 상세에서 상품별 출고 · 선택 출고 · 잔여 일괄출고. 한 confirm = 한 판매 |

### 9.3 진입별 prefill

**A. 생산 직후**

```
생산확정 TX (전량 IN)
→ [바로 판매]
→ salesPrefill (규격·수량 초안, 전량 판매 강제 없음)
→ 판매/출고 화면, 출고방식 기본 DIRECT
→ 1차: 주문 연결 UI 없음 (무주문 DIRECT)
→ confirm
```

생산 화면에서 80/20 분할 입력 금지 (DEC-023). 판매 수량만 줄이면 잔량은 상품재고로 남음.

**B. 주문 상세**

```
주문 10, 배정잔량 6 → 기본 배정재고(STOCK), 출고수량 기본은 잔량 이하
배정 0 → 기본 일반재고(DIRECT)
→ confirm
→ 주문상세: remaining_order[] 로 「출고 n / 잔여 m」
```

무주문+STOCK은 Core가 거부. 화면이 그 조합을 만들지 않음.

**C. 재고 탭 → 직접 판매 (CURRENT + TARGET)**

CURRENT: 담기 → 「판매 미리보기」→ 판매/출고.
TARGET: 선택 집합 + **[직접 판매]** (기존 경로 유지). **[경매 넘기기]**는 §5B · **본 confirm과 무관**.

```
상품 선택 · 수량
→ [직접 판매]
→ 규격 prefill · 주문 없음 + DIRECT
→ 수량 ≤ 가용(표시는 재고 조회 available, 확정은 Core 재검증)
```

선택한 저장일/stock_seq를 payload에 넣지 않음.

### 9.4 확정 후 동선 (1차)

성공: 짧은 완료 안내(`sales_no`) 후 **같은 폼에서 이어서 출고하지 않음**.

- 주문 상세 진입 → 해당 주문 상세 복귀(재조회)
- 재고 진입 → `/orders?tab=stock` (재조회)
- 생산 진입 → `/orders?tab=sales`

부분잔량은 주문상세 **출고** CTA로만 재진입.

실패: confirm 오류 메시지. 재고/화면 수량은 Core 거절 그대로. 로컬 재계산으로 덮지 않음.

### 9.5 구현 시 금지

- Client `stock_seq` 지정
- `remaining_order_qty`만으로 줄 완료 판정
- 판매화면 3벌 복제
- 출고 API를 주문 path로 다시 만들기
- Stage 6에서 판매취소·반품
- **경매 출하를 ShipConfirm/confirm API에 합치기**
